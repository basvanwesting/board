# board: spec

A file-based board for a planner/worker pair of coding agents and their user: one small binary, a CLI for the agents and a TUI for the user's terminal pane. Written by a planner session on 2026-11-20 from a design the owner approved; this file is the first brief of the project. Decisions carry their reason so they can be reopened.

This repo is public: it holds the tool only. No project data, client names or ids in code, tests, fixtures or docs.

## Why

Two agent sessions per project: a planner (designs with the user, writes briefs) and a worker (implements one brief at a time, commits). Naming: `board` is the tool (this repo) and one project's view; `board-data` is the repo that holds every project's board. Until now reports travelled as chat messages between the sessions and the open items lived in files only the planner read, per machine. Problems: worker reports cluttered the design conversation; a report died with its transcript; the user could not pull the open items up; two machines had two boards; commit SHAs noted in items went stale after a rebase.

Principle: the files are the record, a message is only a wake-up. The owner works in a terminal multiplexer (herdr) with three panes: work agent, plan agent, board. No Claude plugins: "file based and cli/tui managed".

## Data: the board-data repo

Separate from this repo: a private git repo named `board-data` (GitHub, over https; its owner is configuration, not this repo's business), one clone per machine at `$BOARD_ROOT` (default `~/Work/board-data`). One directory per project:

```
board-data/
  <project>/
    briefs/128-some-slug.md      open briefs
    briefs/parked/131-….md       parked briefs, waiting for the owner's word
    briefs/done/126-….md         filed briefs
    chores/c12.md                a chore
    backlog/b41.md               a backlog item
```

- The project is found from the directory the command runs in: the path of the repository's checkout relative to `~/Work`, `/` replaced by `-` (`~/Work/shop` → `shop`, `~/Work/tools/shop` → `tools-shop`). `--board <name>` or `BOARD` overrides. Reason: derived from existing state, no marker file in the project.
  - A worktree added with `git worktree add` is on the board of the repository it was added to (`~/Work/shop/.claude/worktrees/x` → `shop`), wherever it is. Reason: its own path is one session's choice and mostly a valid project name, so it would give an empty board without a word, and a write there would start and push a project under that name. Where the repository has no checkout of its own to name it (a bare repository, a submodule's worktree), the command is refused and names `--board`. Rejected: refusing every added worktree, which makes a worker in one name the board on every command.
  - The board-data clone itself gives no project: a command run inside `$BOARD_ROOT` without `--board` is refused and names it. Reason: the clone is a repository below `~/Work` too and the place where items are edited by hand, so its path as a name (`board-data`) would be an empty board, a `lint` that says `ok` right after a hand edit, and a write that starts a project `board-data`. Rejected: taking the project from the directory inside the clone (`board-data/shop` → `shop`), a second way to name a project for one place.
- Three kinds of item:
  - Brief (`128`, a number per project, continuing the existing sequence): a markdown document. Header lines (`id`, `status`, `base`, `closes`, `after`, `first`, timestamps), then the planner's sections, then `## Questions`, `## Amendments` and `## Report` as they come (a question or an amendment under a `### <time>` line of its own; the report last, as it runs to the end of the file). Status: `draft` → `queued` → `started` ⇄ `blocked` → `reported` → `filed` (moved to `briefs/done/`), or `draft` → `parked` (moved to `briefs/parked/`) → `queued` (moved back).
  - Parked (owner, 2026-11-26): a finished brief that waits in `briefs/parked/` until the owner's word releases it, for the small spinoffs the planner can write whole from a report: "a proper brief with status backlog (or maybe even better a folder like filed) which the planner then will ignore on normal queue operations". A folder, not only a status: "If we have a folder (planned) it would be much easier to distinguish briefs during daily build cycles. Otherwise the planned state would be interleaved and messy". As for `done/`, the place decides: a brief under `briefs/parked/` is parked whatever its header says, a header that says `parked` elsewhere is no status, and only `queue` moves on from it. `board park <id>` takes a written draft, with the refusals of `queue`, `--closes` and `--after`, and stamps `parked:`. `board queue <id>` releases one (`--first` allowed; `--closes` and `--after` were set at `park`, and `board after` changes the wait), `board queue --parked` all of them in one commit, with one `queued:` time, so `next` takes them by number. A release asks again what `park` asked (text in every required section, a wait a write would accept), as a parked brief is edited or placed by hand and is built with nobody watching; `queue --parked` checks all first and releases none when one fails, naming it; the `parked:` line stays as the record. `next` never takes a parked brief, `ls` and the plain board do not list one (`ls briefs --status parked` does), a wait on one is not over, and `amend`, `block`, `report` and `file` refuse it as they refuse a draft; it is the planner's to edit by hand, and one no longer wanted is deleted by hand. No way back to draft. The name is the planner's choice among those the owner allowed ("parked or planned is OK"): every brief is planned, `delayed` reads as late, `nightly` fixes a time, `auto` says nothing of what is automatic. A brief whose premises failed at night is reported as not built and filed with `board file <id> --not-built`, which asks for no commit and leaves what it closes on the backlog, for the owner's review. Rejected: a status without a folder (parked briefs interleaved with the day's in every listing); a backlog group of ready spinoffs that the planner briefs overnight (soft logic in group names, and the brief written cold).
  - `reported` waits for the planner's read, not for the user: filing is the designer's read receipt. The report carries deviations from the design the user approved, and its leftovers (what the worker could not do, out-of-scope findings) need the design's context to become chores and backlog items; a worker filing its own brief would force neither. So the planner files at once: when the worker's one line `reported: <id>` arrives (it starts a turn, or is handled before the answer of the turn it lands in), and at the start of every turn for a line held or lost; and what the user acts on is the push, which the `unpushed` label shows (owner, 2026-11-24).
  - `unpushed` is a label, not a status: a filed brief is shown so while a commit with its `Brief: <id>` trailer is in the project repository's `@{upstream}..HEAD`, by the reading of the trailer `file` uses, in one `git log` for all briefs. Nothing stores it; the file says `status: filed`, in `briefs/done/`. Only in the project's own checkout with an upstream: with `--board` naming another project, without an upstream, on a detached `HEAD` or on a branch with no commit yet, nothing is labelled. About this checkout, the one the owner pushes from: another machine shows it until its checkout has fetched the push. Rejected: filing at the push (the leftovers would land after it, among them chores due before it, and reading a report early without filing needs a stored "read" state and a command for it); a stored `unpushed` status (a second copy of what git knows, stale after every push made without `board`); watching the project's `.git` (a watcher on another repository for a label a minute's tick refreshes).
  - Chore (`c12`): the user's own action, in a group (`group:`), with a check if needed (`check:`, one line): how to see it is done, for a chore whose title does not show it. Optional (owner, 2026-11-25: "some chores are just that, simple actions. A check would repeat it"), and then lint does not warn either. Done = its file is deleted; git history is the archive.
  - Backlog item (`b41`): an unrefined item, in a group (`group:`) as a chore is. The owner sweeps the backlog for work rather than ranking it (2026-11-25), and grouping it is "much more useful" than an order (2026-11-26).
  - A chore or backlog item is a file of its own, as a brief is (owner, 2026-11-25), at `<project>/chores/c12.md` or `<project>/backlog/b41.md`: header lines (`id`, `group`, `check` on a chore when it has one, `after` when it waits, `from` when it came from an item, `created`, in that order; a key the tool does not know is kept byte for byte), a blank line, the `# <title>` line, and when there is a body a blank line and the body: Markdown, kept byte for byte (blank lines, code fences, `## ` lines), so a SQL check is copied whole and a list reads as one. The file is named by the ID only: a slug would rename the file at every retitle, and the merge of a rename is not worth it (owner). `ls`, the TUI's rows, the filter and `Y` show an item as the one line it had before, `c12 <title>. Check: <check>  (126)` (no check part without a check) and `b41 <title>  (from 126)`; `show`, the TUI's preview and `yy` give the item's file as stored, byte for byte, as they do for a brief (owner, 2026-11-26: "for briefs it is. Any reason to threat this differently? I would do it like briefs do for chores and backlogs as well"), from one piece of code; the preview highlights its `#` lines as it does a brief's, and the header's `after:` says what it waits on. This replaces the line, a blank line and the body, a form from the list files, where an item had no header. Rejected: the header in the preview and `yy` only, with `show` left as line and body (two forms of the whole item); the `ls` line above the header (the title and the check would stand twice). This reverses the decision of 2026-11-24 for one file per kind, for the owner's reasons: a body of indented lines without blank lines does not read as Markdown, an SQL statement for validation is hard to copy as one unbroken line, and one file per item is better for git (a merge of two items never meets). What one file per kind gave, and what took its place: order and groups (then the `order` and `group` keys: "both could be metadata at the start of the body", and "why not let J/K move order?"; the order went on 2026-11-26, below), the ID-keyed line merge (now one file per key, as for a brief), and adding an item by typing a line (now `board add`; the tool gives no ID to a hand-made file). Rejected: a slug in the file name (above); prefixing briefs (their `Brief:` trailers are in pushed history); the check in the body (lint and `add` would have to find it in free text).
  - Groups, no order (owner, 2026-11-26): chores and backlog items are listed by group (by name, byte order; a group exists while an item names it), then by ID, numerically (`c9` before `c10`), which is the order they were made in. "These items don't have order"; the only real order is the brief queue's. This reverses the `order` key, `board move` and the TUI's `J`/`K` of 2026-11-25: "no more move on chores and backlog. Chores should be a short list anyway and backlogs grouping is much more useful". The group is required on both kinds ("Make it required, just add "Default" to start with and then the logic is easier"): `add` without `--group` writes `group: Default`, an inbox the planner sorts. The groups are the planner's to name and keep balanced, but for `Spinoff`, the one name the planner skill fixes for the items it adds from a brief's report (owner, 2026-11-26: a separation "between user created backlogs and brief spinoff artifacts"); the tool keeps no list of them. `board group <id>… --to <name>` changes the group of chores and backlog items, mixed, in one commit, so renaming or merging a group is one write; the name is behind `--to` because with two bare positions a call that forgot it would read the last ID as the name and regroup without a word. An item in the group already is left out of the commit and of what it prints; when that is every item, nothing is committed. An unknown ID refuses the whole command. A `group:` line added to an item without one goes right after `id:`. An item file without a `group:` is listed under the empty name and is a lint finding, but no command refuses it: it is seen and listed, unlike the list files of the older storage. Rejected: a backlog item without a group as an ungrouped inbox (one rule for both lists); keeping `order` and `move` for chores only (a short list needs no order).
  - Waits and the queue (owner, 2026-11-26: items "might have a dependency to another item (brief/chore/backlog) more as a linked list. And only a few actually have dependencies. The only real order is the briefs"): `after: <id>` in the header of a brief, a chore or a backlog item names one item of the same board it waits on. One predecessor: a sequence is a chain, and a row shows one ID; a brief that needs two goes after the later one. A wait is over when its target is a brief that is reported or filed, or when no file with that ID is on the board (a chore done, a backlog item dropped or closed, a brief deleted by hand). Enforced only by `next`, which claims the first queued brief whose wait is over; a waiting brief holds up only itself and what is chained to it, and on chores and backlog items the wait is shown, never enforced. So no order of the queue can break a dependency, and `--first` needs no check of its own. A write refuses a target that was never given (past the highest ID or number ever used, which only a write reads, from history), the item itself, a target whose own chain leads back to it (two briefs waiting on each other would never be claimed), and for a brief a backlog item it closes (the item goes only when the brief is filed), checked again at `queue` for the `after:` a draft has; a target whose wait is over already is accepted. A row and an `ls` line end with `  after <id>` while the wait lasts, set off by two blanks as the reference `  (126)` is, so it is not read as part of a chore's check. Lint reports the last two in files edited by hand; a hand-written `after:` to an ID never given has no file, so it holds nothing up. The queue is reordered by putting one brief first ("first only is OK"): `queue <id> --first` writes `first: <n>`, one above the highest among the queued briefs, so the latest `--first` wins (on a brief that is first already, alone, it writes nothing, so a press of `F` too many is no commit); queue order is the briefs with `first:`, highest first, then by `queued:` time, then by number. A counter, not a time: a stamp is whole seconds, and two `F` presses in one second would tie. Two clones marking offline can give one number, and the tie goes by the rule after it: it takes an offline write. Rejected: full up/down with an order key on briefs (the owner: first only); several predecessors (a chain says a sequence, and one ID fits a row); moving a brief first by rewriting `queued:` (a false time); checking `--first` against `after:` (`next` skips a waiting brief).
- The ID is the first word of an item's line, so it copies cleanly and greps.
- Plain markdown, editable in vim. The parsers take anything; `board lint` (also run after every write) reports what leaves an item unusable: an item's header `id:` that is not its file name's, a missing required key (`id`, `group`, `created`; an empty `group:` counts as missing, and its finding names `board migrate`), a missing title line, an `after:` that is no ID, on the item itself, in a loop or on a backlog item the brief closes, a brief number on two files, a brief with an unknown status, a file below `briefs/`, `chores/` or `backlog/` named outside the grammar (not synced).

## Commands

```
board                          TUI on a terminal; the plain board when piped
board ls [briefs|chores|backlog] [--status <s>]   the open briefs include the unpushed ones; --status takes a status or unpushed
board show <id>                a brief's or an item's file, as stored
board new brief <slug>         → path; header written (status draft, base = project HEAD)
board queue <id> [--closes b41,b52] [--after <id>] [--first]   a draft, or a parked brief (then only --first); refuses an empty required section; --first alone also on a queued brief
board queue --parked           every parked brief, one commit, or none when one is not written whole; `nothing parked` when there is none
board next                     worker: claim the first queued brief that waits on nothing (status started) → path; else `queue empty`, or `queue empty, 2 waiting on c9`
board block <id> "<question>"  status blocked, question appended under ## Questions
board amend <id> [--replace]   stdin appended under a brief's ## Amendments (a blocked brief resumes), or to an item's body; --replace rewrites the body
board report <id>              stdin becomes ## Report; status reported
board file <id> [--no-commits | --not-built]  reported brief: verify its commits in the project repo, delete the backlog items it closes (not with --not-built), move to done/
board park <id> [--closes b41,b52] [--after <id>]   a written draft to briefs/parked/, until `queue <id>` or `queue --parked` releases it
board add chore "<text>" [--group <g>] [--check "<c>"] [--after <id>] [--from <id>] [--body]
board add backlog "<text>" [--group <g>] [--after <id>] [--from <id>] [--body]   --group: Default without it; --body: stdin is the item's body
board done <c-id>…             board drop <b-id>…
board retitle <c-id|b-id> ["<text>"] [--check "<c>"]   title or check (--check "" removes it); its ID, group, reference and body stay
board group <c-id|b-id>… --to "<name>"   chores and backlog items into a group, one commit
board after <id> <target> | --none   what an item, or a draft or queued brief, waits on
board sync                     board lint
board migrate                  the project's chores.md and backlog.md → item files, and the item files up to date, one write
```

- Output is plain, stable text (agents read it); no JSON until something needs it.
- Required brief sections (for `queue`): Task, Design, Premises, Out of scope, Verification, Not doable by the worker, Worker protocol. The template text is the planner skill's, not the tool's: agent rules stay under the owner's review, a data repo or a binary is the wrong home. The skill's draft is this project's to keep true: `skill/my-plan.SKILL.md` (the planner skill as it will read once the CLI exists; every command it names must exist as it names it; a test in `src/main.rs` parses each `board` invocation in its code with the CLI's own definition). It is installed by the owner, who copies it into the chezmoi source (`dot_claude/skills/my-plan/SKILL.md`) after approving it; this project never writes there.
- No roles or auth: which session runs which command is the skill's convention. But `report` and `block` touch only status and their own section, never the planner's text.
- `amend` takes a queued, started or blocked brief: a draft is still the planner's to edit, and a reported brief is done, so what is decided after the report belongs to the next brief; there is no way back from reported (owner, 2026-11-20). A question or an amendment with a `## ` line outside a code fence is refused (use `###`): it would split the brief's section. So is one that opens a fence and leaves it open, which would turn the sections after it into quoted text. A report may hold anything: it is the last section.
- `amend` of a chore or backlog item appends stdin to its body after one blank line, with no timestamp and no status: an item has neither, and its body is the planner's text to date as it sees fit. `--replace` puts stdin in place of the body, and empty stdin then removes it (owner, 2026-11-24): the planner changes single items only through `board`, and append-only bodies collect text that is no longer true; appending stays the default, as it cannot lose text on the clone. An item changed on two clones before either synced keeps the remote's file, and the clone's is saved beside it (Sync): a body is rarely written from two clones at once. `--replace` on a brief is refused: its amendments are a record of what was decided when. `add` reads a body only with `--body`, never "stdin when there is some": an agent's stdin may be a pipe that never closes, and on a terminal the command would wait for the user. Empty stdin is refused, but for `--replace`; stdin without a final line break gets one. `retitle` changes an item's title, below.
- `retitle` replaces an item's title, and a chore's check with `--check` (alone, only the check; `--check ""` removes it): the user refers to items by ID, and without it the planner, which changes single items only through `board`, could change a title only by drop and add, a new ID. The ID, the group, the reference, the body and every other key stay byte for byte. Not for a brief: its title is in its file, its slug in the file name. An item retitled on two machines before a sync keeps the remote's (Sync). Rejected: `edit` as the name (it reads like the TUI's `e`, the editor); `--group` (`group` owns the group); `amend --title` (amend writes the body, and `--replace` would become ambiguous).
- `file` verifies commits by the trailer `Brief: <id>` on a line of its own, in the repository the command runs in (also with `--board`), reachable from HEAD: the worker puts it on every commit of a brief. Decided by the owner, 2026-11-20, over SHAs noted in the report: a rebase changes every SHA and keeps the message. A brief without any such commit is not filed (`--no-commits` for a brief that changed nothing in the repo). Filing is one commit: the files of the backlog items `closes:` names are deleted, the brief is stamped filed and moved to `briefs/done/`; it prints `filed 128 (3 commits) closed b41`. An item already gone (dropped since the brief was queued) is skipped, as the item is closed either way.

## Sync

The tool is the only thing that runs git in the board-data repo. It pushes: the board-data repo is data, the owner's "never push" rule for code does not apply to it (confirmed 2026-11-20: "a totally different scope, intention and ruleset").

- Every write: take a lock (two sessions on one machine share one clone), commit hand edits to board files (`board: hand edits`), fetch, merge, apply the change on the merged state, commit only the touched paths (one commit per command, subject `<project>: <what>`), push, then fast-forward the checkout. Every write commits hand edits, not only `sync`: the change applies to the merged commit, so an edit left in the worktree would take no part. A file saved while the write runs is never overwritten: the fast-forward refuses, and the save is committed and merged in, by the rule below (a save of a file the write changed too is kept as its `.local` copy). A file deleted while the write runs is committed as deleted before the fast-forward, which would otherwise write it back without refusing.
- A hand edit is also how a sweep is written (owner, 2026-11-25): an agent changing many chores or backlog items at once (retitle them all, give them all bodies) saves their files and runs one `board sync`, not one command per item. Every write is a fetch, a commit and a push, and a run of them back to back crowds out the other sessions' writes: in the case measured, one session made 107 writes in eight minutes and every other session's write lost all four rounds it then had. The retries below and local-first writes make that survivable; the sweep keeps it from happening. Rejected: a batch form of `amend` and `retitle` (a command format to parse and test for what an editor save and a sync already do).
- Local commits (hand edits, offline writes) join the remote's by a merge commit (`board: merge`), never by a rebase: ancestry then records what is already pushed, so a crash between push and local update cannot apply a hand edit twice. Cost: merge commits in history when both sides changed.
- A failed push: unless one of the command's pushes is found to have landed (its commit is an ancestor of the fetched remote; a push can reach the remote and still report failure, even after the next fetch, and re-applying then would publish the item twice), the command's commit is dropped and the command applied again on the fresh remote state, at most 8 pushes for a refereed write and for `board sync`, 2 for a local-first one (below); an ID is printed only after the push that publishes it, so nothing is ever renumbered. A command's commit carries a mark of its run (`Board-Run:`): two clones of one user making the same change on the same commit in the same second would otherwise make the same commit, and each would take the other's push for its own (two workers handed one brief by `next`). A write's last failed push counts as offline, even with a working fetch: an agent's command must end rather than retry without limit, and an ID not yet published may not be printed.
- Two kinds of write (owner, 2026-11-27: "local first as default and refereed as explicit exceptions on add, new, next"; with one file per item, a commit left on the clone merges cleanly later, so "the sync is low risk later anyway and can be delayed"). Refereed: `add chore`, `add backlog`, `new brief` and `next`, whose ID or claim is good only once pushed: 8 rounds with the waits below, refused when none is pushed. Local first: every other command that writes, `migrate` and the TUI's writes among them: 2 rounds, the second at once; when both pushes fail, the one more fetch finds a push that landed after all, else the command runs once more on the clone and succeeds, its commit left there for the next write that pushes (note `not pushed yet: <n> commit(s), they go out with the next write (<reason>)`; `not pushed: …` stays for a remote not reached and for a refereed write or a sync). The kind is stated where the command is defined, local first unless said; allocating an ID or claiming in a local-first write is refused, so a new command cannot hand out an ID unpublished. `board sync` keeps the 8 rounds: it changes nothing of its own and is what publishes what local-first writes left on the clone, so giving up after two would defeat it. Nothing pushes on its own later: the next write that reaches the remote, or `board sync`, carries the commits. Rejected: a branch or a repository per project (a checkout per project and a migration on every machine); IDs given without the remote (costs the short `b41` the owner speaks in); merging the lost commit in the retry instead of applying the command again (a second way to build a round).
- A push that lost a race (the remote's `main` moved after the fetch: git's non-fast-forward refusal, or the remote's failed ref update) is retried after a random wait, from zero up to a ceiling that grows per retry: none after the write's first lost race, then 0.25 s, 0.5 s, 1 s, 2 s, 4 s, 4 s after the next ones, at most 11.75 s in all (owner, 2026-11-25: "syncing with push/pull should just use a random retry and backoff"; it reverses that day's earlier rejection of a wait and of more rounds, made with the sweep above). A retry made the instant a push is refused can fall in step with a writer that pushes on a steady cycle: when a round takes about as long as that cycle, every retry starts at the same losing point of it, so every round is lost, not most, as measured. A random wait makes each round an independent try, eight rounds make enough of them (a local-first write's one retry follows the first lost race, so it never waits), and the first lost race is retried at once because one collision is the common case. Counted in lost races, not rounds: a round lost otherwise says nothing about a writer in step. Any other refused push (a hook that declines, a dropped connection) is retried at once, and a failed fetch goes offline at once: waiting helps neither. The clone's lock stays held across the waits, so other writes on the machine queue behind them. Rejected: a fixed wait (two starved writers stay in step with each other); a time budget instead of a count (the bounded waits are one); a switch that zeroes the wait for tests (the tool has no seam for its tests; the waits are tested below the binary).
- Offline: a write that allocates an ID is refused, and so is `next` (a claim is shared like an ID: two offline claims of one brief would conflict); other writes commit locally and are pushed by the next command that reaches the remote. Accepted by the owner, 2026-11-20: "we need to be online for the agents anyway".
- The next chore or backlog ID and the next brief number are one past the highest ever used in git history (every item file ever added under the project's `chores/` or `backlog/`, and every ID the old `chores.md` and `backlog.md` ever held, as a board converted from them has the IDs of what was done before only there; the files ever added under `briefs/`), not only among what is there now: a deleted item or a hand-deleted brief would otherwise free its number, a `closes b41` or a note would name a new item, and `file` would count the old brief's `Brief:` commits. History is the counter, so a shallow clone is refused. Not followed across a rename of the project's directory: what was deleted before such a rename frees its number. Rejected: a counter file, which a hand edit makes stale.
- A brief is one key in all three places (`briefs/`, `briefs/parked/`, `briefs/done/`): a brief parked, released or filed on one machine and changed on the other is the changed-on-both case below.
- A chore or backlog item is merged by its file, which is its ID: changed on one side, that side's; changed on both, it follows a brief's rule below. Adds from two machines both survive, with different IDs, as an ID is given only on the remote's tip. One exception to the brief's rule: an item deleted on one side and changed on the other is deleted, either way round, and no copy is made (owner, 2026-11-25): a done chore that keeps nagging through lint is worse than an edit that is in the history. A `group` of many items met by another machine's write of one of them is the changed-on-both case for that item's file. Rejected: a field-by-field merge of an item changed on two machines (one rule for every file, and it takes an offline write to meet it).
- A brief or an item changed on two machines is never merged as text: the remote version stays, the local one is saved beside it as an untracked `<file>.local`, and `lint` reports that copy after every write in its project until it is deleted. Rejected: stopping the sync, which blocks every project on that machine with git by hand as the only way out. See Open points.
- Reads never touch the network. The TUI fetches in the background about once a minute and shows the clone's unsynced commits (`2 unsynced`: not `unpushed`, the label of a brief), commits the remote is ahead and the last fetch in its status line; the fetch takes the write lock and is skipped when a command holds it, so every git process in the clone still runs under the lock. It only fetches: committing and pushing on a timer would publish a half-finished hand edit, and the owner wants commits on meaningful transitions only (2026-11-21).
- Shell out to the `git` binary (the machines' credential helper already handles https); no libgit2.

## TUI

`board` on a terminal, laid out like LazyGit (owner, 2026-11-21): panels inside one terminal pane, built for a wide one (about 200 columns; no narrow layout, nobody uses one).

```
╭─[1]─Briefs (2) - Parked (0) - Filed─╮╭─[0]─128 some-slug─────────────────────────╮
│▶128 started   some-slug        42m  ││id: 128                                    │
│ 127 reported  other-slug            ││status: started                            │
╰─────────────────────────────────────╯│                                           │
╭─[2]─Chores (1)──────────────────────╮│# Title                                    │
│ ## deploy                           ││## Task                                    │
│ c12 Rotate the key. Check: …  (126) ││…                                          │
╰─────────────────────────────────────╯│                                           │
╭─[3]─Backlog (1)─────────────────────╮│## Report                                  │
│ ## Default                          ││                                           │
│ b41 …                    (from 126) ││                                           │
╰─────────────────────────────────────╯╰───────────────────────────────────────────╯
 shop · fetched 1m ago · 2 unsynced · 128 started 42m         d done  e edit  ? help
```

- Left, about 45% of the width and at most 90 columns: three stacked panels, each with its own cursor; the focused one takes the spare height. Briefs (tabs Briefs, the open ones and the unpushed, Parked, the briefs in `briefs/parked/` by number, and Filed, the others; started and blocked first, then reported, unpushed, queued (in queue order, so a brief put first shows first), draft; the set of unpushed briefs is asked of git on a thread of its own, at each load (so on `r`) and about once a minute, one question at a time and apart from the fetch, which can stall on the network: a push shows within the minute), chores and backlog by group, by ID within one. Titles as LazyGit draws them (owner, 2026-11-23): the jump key in brackets, then the tabs separated by ` - `, the panel's name being its first tab; the tab shown is bold, green when the panel has the focus. Each tab but Filed carries the number of items it lists, headings left out (owner, 2026-11-26: "We should probably add counters to the headers"; Filed none: "it isn't really actionable"): `Briefs (3) - Parked (2) - Filed`, `Chores (5)`, `(0)` for none; under a filter the matches of all, `Backlog (3/10)`, for each counted tab of the panel, as a bare count would read as what is left. The count has its tab's style. `board ls` and the piped board print no counts: agents read them. Rounded corners. The preview is `[0]`, as LazyGit numbers its main view, with the same green; its number shows with nothing to preview too, as it names the pane. The number is a key, `0`, as on the panels: a number without its key would promise a jump that is not there. A line too long for its panel is cut there and whole in the preview.
- Colour: an item's ID is cyan, in its panel and in the preview's title; an open brief's status is coloured by what it asks of the user (`blocked` red, `started` green, `unpushed` yellow, the one row that asks something of the owner, `draft` dim, `reported` and `queued` plain: reported waits for the planner); the age of a brief in flight is dim, and so is the `  after <id>` a row ends with while it waits (shown as `ls` shows it, gone once the wait is over, and part of what `Y` yanks). Only the terminal's 16 named colours, never RGB or indexed: the user's terminal theme decides what they look like, so the board reads on a light and a dark theme, and there is no second theme to maintain. Headings, references, the preview's body and the brief in flight on the status line stay plain: the ID and the status are what the eye looks up.
- Right: the preview follows the cursor: a brief's or a chore's or backlog item's file, as `show` prints it, wrapped. Plain text, headings highlighted; no markdown renderer, which is much machinery for a pane briefs are read in.
- Bottom line: project, sync state, the brief in flight and for how long, then key hints. Confirmations, sync notes and errors show here too.
- The TUI edits no text: `e` suspends it and runs `$EDITOR` on the brief's or the item's file, and syncs on return (which commits the edit). It waits for the TUI's own writes to end first: an editor opened beside one reads the file before the write changes it, and saving would put back what the write took out. Any key but Esc calls the wait off, so the editor never takes the terminal while keys meant for the TUI are being typed. Its only writes are whole-item actions.
- Keys, vim-flavoured: `j`/`k`, `gg`/`G`, `ctrl-d`/`ctrl-u`, `/` filter (the focused panel), `1` `2` `3` or `h`/`l`/Tab/Shift-Tab focus a panel, `[`/`]` step through the Briefs tabs (Briefs, Parked, Filed) and stop at the ends, `0` or Enter focuses the preview for scrolling (with an item under the cursor), `y` yanks the ID, `Y` the line (as `board ls` prints it), `yy` the whole item (as `board show` prints it, from the same code, as text like every yank: bytes that are not UTF-8 become U+FFFD; the second `y` replaces the ID on the clipboard, read as `gg` is, with no timer; nothing is cut to fit), `d` done (chore), `x` drop (backlog), `F` first (a queued brief: `queue <id> --first`, with no question, as a second `F` on another brief undoes it; on another brief a note, on a list item nothing), `e` editor, `r` sync, `?` help, `q` quit (ctrl-c too, from anywhere: raw mode makes it a key). `d` and `x` ask once, on the bottom line: `y` is yes, any other key no. A brief has two actions: `F` on a queued brief (owner, 2026-11-26: "it needs a single key in the TUI on a brief as well"), and `Q` on a parked brief (owner: "Q is fine"), which runs `queue <id>` after asking once on the bottom line as `d` and `x` do: nothing takes a brief out of the queue again, and `Q` is one Shift away from `q`. `F` does nothing on a parked row: in the TUI it would release a brief unconfirmed. Queueing a draft and filing stay the planner's. Quit waits for the TUI's writes to end, so what the screen showed done is on the board; a second quit does not wait (a push can stall as long as the connection does).
- Esc leaves the preview, closes help, answers no to a confirmation or clears a filter, and does nothing else: the owner hits Esc by reflex.
- Every action is a CLI command, so an agent can do what the user does, and the TUI calls the same function the command does (in process, not a second `board`). Items have no order, so no key moves one (Data, Groups); regrouping is `board group`, the planner's.
- A command runs on a worker thread, one at a time, so navigation never waits for the network. Results and the commands' notes show on the bottom line.
- The mouse is captured (owner, 2026-11-25: "I'm leaning towards allowing mouse capture, because LazyGit does the same and we are using that as a UX base"): a left click focuses the pane under it (a list panel, or the preview when `0` would, with an item under the cursor; its border and title count) and selects the item on the row clicked, as the screen drew it; a heading, a row below the last and the status line select nothing. The wheel does what `k`/`j` do in the focused pane: capture takes the terminal's own wheel away. A click is first an unrelated key, then a click: it clears a pending `g` or `y` and calls off an edit waited for; it does nothing while the filter is typed, a question is asked, help is open or a quit waits. The capture is on while the TUI holds the terminal and off wherever it gives it back: at its end, while the editor runs and on a panic. The cost: the terminal's own selection needs its bypass (Shift-drag in most); `y`, `Y` and `yy` copy. Rejected: keeping the first spec's "no mouse capture, so the terminal's own selection and copy keep working" (the owner asked for the click, and the yank keys copy); a focus that leaves the selection elsewhere (reads as a miss); a setting to turn the mouse off (a second mode to test, for a cost the bypass covers); drag, double click, other buttons and hover. Yank through OSC 52, and through `wl-copy` (under Wayland) / `pbcopy` (macOS) when present.
- Redraw when a file under the board changes (the worker's `next` and `report` show at once); the cursor stays on its item, not its row.
- Tests: the state is a pure function of events (key, mouse, resize, clock tick, file change, command result) giving the new state and the commands to run; a tick carries the time, and the fetch timer compares it with the time of the last fetch asked for, so a trace drives the timer by the times it sends, without waiting. Trace-test it with random event sequences; after every step: the cursor is on a row that exists and on the same item across a reload, Esc never starts a command and navigation none, `d`/`x`/`Q` never run unconfirmed (no key releases a parked brief unasked), `F` sends one `queue --first` and only on a queued brief. Rendering is tested against ratatui's in-memory screen; the runtime (worker, editor, yank) against the real sync loop, on a screen in memory.

## Consolidating the old planner folders: not this tool's job

No `import` command. Each project's old planner folders (one per machine: `backlog.md`, `chores.md`, `queue/`, `sent/`, `done/`) are moved onto the board by that project's own agents, who know what the items mean and can merge two machines' lists with judgement (the owner, 2026-11-20: "the agent only needs CRUD tools from the cli for it to do so"). What that asks of the tool, all of it ordinary use:

- `board add chore|backlog` for every open line (IDs are assigned fresh; nothing refers to old ones).
- Filed briefs are an archive: the agent copies the old files into `briefs/done/` and runs `board sync`, which commits hand-placed files as it commits hand edits. `lint` accepts an archived brief without the header the tool writes (number and slug come from the file name).
- The next brief number is one past the highest number among open and filed briefs, those deleted since included (Sync), so a project's sequence continues.

## Upgrading a board from list files

Before item files a project's chores and backlog were `chores.md` and `backlog.md`, one line per item. `board migrate` converts both in one write (one commit that adds the item files and deletes the lists, pushed under the lock and the retry like any write) and prints what it made (`migrated 14 chores, 114 backlog items`). In the same write it brings the item files up to date (below), alone when there is no list (`updated 151 item files`); with nothing to do it says `nothing to migrate`.

- A line is read by the old tool's own line readers, kept for this, so it is taken apart as the old tool did. An item keeps its ID; a chore's `group` is the heading it stood under, a backlog item's `Default`; no `order` is written. The title is the text as the old `retitle` saw it, without the check, its join and the reference; the old writer joined text and check with `. `, or one space after a text ending in `.`, `!` or `?`, so a text that ended in `.` and one that did not read alike, and both lose the full stop (the join puts it back: `ls` shows the line as before); a full stop after `.`, `!` or `?` is the text's own (`Wait...`). `check`: what followed the last `Check:`, none when there was none. `from`: the reference's ID as written, whatever its kind. The body: the continuation lines without the body's indentation (the two spaces the tool wrote, or the one character of a line typed with one space or a tab), the rest byte for byte. `created`: the time of the migration, as the lists never recorded one.
- Item files from before groups on the backlog (2026-11-26): an item without a `group:` line gets `group: Default`, right after `id:` (an empty `group:` is filled where it stands), and every header `order:` line goes. Nothing else of a file changes: unknown keys, the title and the body stay byte for byte (a body line that reads `order: 3` is body), and a file that needs neither change is not in the commit. The order lines are stripped although nothing reads them: migrate rewrites these files anyway, and a dead key in every file would have to be explained to each planner who edits one by hand.
- Refused, nothing changed and each line named, for the owner to fix by hand and run again: free text (a `# ` title line included), an item without an ID, an item without a title (`- c12` alone), a chore above the first heading, a heading in `backlog.md`, two items with one ID, an ID that has an item file already, a CR line end, a heading, title or check that is not UTF-8. Rejected: giving a colliding ID a new number (an ID is how the owner and the briefs refer to an item; a hand fix is right for a case that takes a forgotten machine).
- While a project has a list file, every command but `migrate` is refused on it and names `board migrate`, reads and the TUI included: a board that looks empty, or a write beside items it cannot see, is what the refusal prevents. Checked in the files and in the commit a write applies to, so a list that comes in with the merge is caught too. A list edited by hand is committed as any hand edit, so a fix after a refusal is what the next `migrate` converts. In a merge, a list the remote deleted (a migration) and the clone changed (an old binary's offline write) is kept, to be refused and folded in rather than lost; changed on both, the remote's stays, as for any file not the board's. A write in another project of the clone is not refused for them and does not convert them; like any write it commits a hand edit to one. `migrate` in a project that has item files folds the list in.
- Nothing guards against a binary from before item files: to it a missing list is an empty board, `add` writes a new list, and `sync` succeeds, so nothing left in the data can stop it. The owner closes the machines instead (2026-11-25, three machines, one in daily use): on the machine in use, rebuild and run `board migrate` once per project; every other machine stays closed until it is rebuilt. One opened with the old binary after the migration can write a list file again; the new binary then refuses that project until `migrate` folds the list in. The same holds for a binary from before groups on the backlog: it writes `order:` and backlog items without a group, and its lint asks for `order`, so a machine stays closed until it is rebuilt and `migrate` has run per project. Rejected: a format marker (shown impossible, above); the new format on a new branch with `main` locked on the remote (stops an old binary's pushes, but needs branch switching in the tool and a manual lock, for machines one owner can close); converting on the fly at the next write (a second, silent way into the new format); `created` from each line's history (a reader of old history for a date nobody reads).

## Quality bar

The owner's rules (global CLAUDE.md) apply: guarantees over prose, commit when green, fresh-eyes review.

- Tests run the real thing: temp dirs, a bare repo as the remote, two clones.
- Trace-test the sync: random interleavings of the writing commands and hand edits of item and brief files on two clones (with pushes failing and going offline in between); after every step: one file per ID with that ID inside, no item lost but by a delete or by the `.local` rule, a body one writer's whole, an item a `group` named in that group where no other write met it, no brief started while what it waits on is not over, none started from `briefs/parked/`, one file per brief number over its three folders, a misnamed file never committed; both clones converge after a sync. Prove the check is not vacuous by breaking the lock or the retry once.
- No sleeps in tests.
- Parser round-trip: reading and writing an item's or a brief's file changes nothing but what the command changed (hand edits and unknown keys survive).

## Build order

1. CLI (everything under Commands and Sync). The planner skill switches to it when this is done; each project's agents then consolidate their old folders onto the board.
2. TUI, in two commits: the read-only TUI (panels, preview, navigation, filter, tabs, help, file watcher, background fetch and status line); the actions (`d`, `x`, `e`, `r`, yank).
3. Later, only if asked: chore checks the tool can run itself (a command per chore, run on demand, never automatically); herdr pane metadata.

Stack: Rust, `clap`, `ratatui` + `crossterm`, a file watcher (`notify`), property tests (`proptest`). Install with `cargo install --path .` on each machine.

## Not in scope

- A Claude plugin, a web UI, a daemon or a systemd/launchd unit.
- Sending messages between sessions: the skill does the wake-ups (planner → worker "queue has work", an answer to a block, a decision made while a brief is in flight; worker → planner "blocked" and "reported"), each one line that points at the board.
- Notifications: herdr already shows the worker's state.

## Open points

- A brief changed on two machines: copy-and-continue (Sync) is chosen while the board has one user, the owner, who consolidates `.local` copies by hand. Reconsider when it has more; the alternative is stopping the sync and printing the git commands that resolve it.
